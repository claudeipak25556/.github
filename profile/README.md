<p>代理配好之后连不上，是运维里最常见也最耗时的场景。多数人凭感觉试：换协议、换端口、重启程序，运气好碰对了，运气不好折腾一下午。更有效的做法是先把故障拆成一棵树——连不上、连上不通、通了会掉，三类现象对应完全不同的排查路径。这篇按这棵树的三个分支走，每个分支给出具体的状态码、命令和参数，最后压成一份上线前必跑的单子。</p>

<h2>一、先画故障树：连不上、连上不通、通了会掉</h2>
<p>三类现象的分界很清楚。连不上是 TCP 层没建立，报连接超时或被拒绝；连上不通是握手成功但请求失败，通常带状态码；通了会掉是请求成功过，运行一段时间后中断。先归类，再往下查，能省掉大量无效尝试。</p>

<h3>怎么快速归类</h3>
<p>用一条带详细输出的请求看结果：连接阶段报错属于第一类，返回 4xx 或 5xx 属于第二类，前几分钟正常、之后断流属于第三类。三类之外还有一种隐性故障——请求成功但出口地址不对，这类要靠主动查询出口地址来发现，不能只看成功与否。</p>

<h3>先把变量固定下来</h3>
<p>排查期间只改一个变量：这次只改鉴权，下次只改端口，再下次只改白名单。同时改三项，即使恢复了也不知道是哪一项起的作用，下次遇到同样问题还得从头试。</p>

<h2>二、分支一：407 和 403 分别指向什么</h2>
<img src="/tp.png" alt="住宅IP代理鉴权失败与白名单拦截的状态码区分">
<p>这两个状态码经常被混为一谈，实际指向完全不同的两层。407 是代理层要求身份验证，403 是代理或目标站拒绝这次访问。看到 407 就往凭据上查，看到 403 就往来源地址上查。</p>

<h3>407：凭据本身或传输方式有问题</h3>
<p>常见原因有三个：用户名或密码含特殊字符未做编码、鉴权方式选错（比如服务端只支持基础鉴权而客户端发了摘要鉴权）、以及凭据在白名单模式下被忽略。命令行里最直接的验证是带凭据请求一次，看返回是否从 407 变成 200；如果仍然 407，先怀疑字符编码，把密码里的符号替换后再试。</p>

<h3>403：来源地址不在允许列表</h3>
<p>白名单模式下，代理只接受来自指定源地址的连接。这里最容易搞错的是"哪个地址"：白名单里要填的是你发起请求的那台机器的公网出口，不是代理自身的地址，也不是你本机的内网地址。先查本机公网出口，再填进去，顺序不能反。</p>

<h3>两种模式怎么选</h3>
<p>固定出口的环境用白名单更省事，不需要在代码里放凭据；出口会变的环境用账号密码更灵活，但要保证凭据不落到日志里。两种可以同时开，此时以白名单优先，凭据错误也可能被放行，排查时要分开验证。</p>

<h2>三、分支二：白名单和本机出口的先后关系</h2>
<p>白名单的问题几乎都出在顺序上。正确顺序是：先确认本机出口地址，再加白名单，然后测试，最后固定出口。反过来做，加进去的地址可能几分钟后就变了。</p>

<h3>先查清本机的公网出口</h3>
<p>用一条查询接口看当前出口，注意区分 IPv4 与 IPv6：有些环境两个协议栈的出口不同，白名单只加了 IPv4，浏览器走 IPv6 就绕过了代理。查完把结果记下来，同时确认这个地址的租期有多长。</p>

<h3>出口会变怎么办</h3>
<p>三条路：向运营商申请固定地址；用动态域名把变化的地址映射成固定域名，前提是服务商支持域名白名单；或者改用账号密码鉴权，绕开白名单的限制。三条各有代价，固定地址最稳但可能产生费用，动态域名依赖服务商支持，账号密码要把凭据管理做好。</p>

<h3>加完白名单要立即验证</h3>
<p>加完不要等，马上发起一次请求，看是否从 403 变成 200。生效通常很快，但部分平台有缓存，需要等一到两分钟。验证通过后再去配置业务程序，避免把代理问题和程序问题混在一起排查。</p>

<h2>四、分支三：断线重连的超时参数怎么排</h2>
<p>断线是三类里最难定位的，因为它不报错，只是慢或者中断。多数断线不是线路故障，而是超时参数排得不合理：连接超时设得太长，卡住时不切换；空闲超时设得太短，长对话中途被回收。</p>

<h3>三个超时要分开设</h3>
<p>连接超时控制建连阶段，建议 5 秒，超过就换下一个节点。读超时控制等待响应的时间，长回复场景建议 60 到 120 秒，设太短会把正常的长输出误判为超时。空闲超时由代理侧控制，问清楚是多少秒，让客户端心跳小于这个值。</p>

<h3>心跳与重试要配套</h3>
<p>心跳建议 30 秒一次，低于代理侧空闲超时的一半。重试建议最多三次，采用递增间隔，并且只对幂等请求重试——对话类请求重发可能产生重复计费，需要业务层做去重。重试时是否换出口，要提前定好：换出口能提高成功率，但会让出口地址变化。</p>

<h2>五、压成一份上线前必跑的单子</h2>
<p>把上面三个分支的检查合并成一份清单，每次换线路、换配置、换环境都跑一遍。跑完再上线，能把大部分问题挡在业务之前。</p>

<h3>五项必测</h3>
<p>一，带凭据和不带凭据各请求一次，确认状态码符合预期；二，查一次出口地址，确认与预期地区一致；三，跑一次 120 秒的长连接，确认不被中途回收；四，主动断开网络 10 秒再恢复，看是否自动重连；五，把请求并发提到日常峰值的两倍，观察是否出现 5xx。</p>

<h3>记录与回归</h3>
<p>每次测试把结果记成一行：时间、配置版本、五项结果、异常描述。下次改动前先看一眼历史记录，能快速判断是这次改动引入的问题，还是原本就存在。这套记录做满一个月，排查效率会有明显提升。</p>

<h2>常见问答</h2>
<h3>代理地址能访问，但业务程序连不上，问题在哪？</h3>
<p>答：先看程序用的是不是同一套网络栈。有些运行环境不读系统代理，需要显式配置；有些容器环境没有把环境变量传进去。用同样的命令在程序和命令行各跑一次，结果不同就锁定在程序配置上。</p>
<h3>SOCKS5 和 HTTP 代理能混用吗？</h3>
<p>答：不能直接混。客户端必须按服务端支持的协议发起握手，用错协议通常表现为连上但无响应。部分服务商同时开两个端口，按端口区分协议，配置时确认端口对应哪一种。</p>
<h3>为什么白天正常，晚上频繁断线？</h3>
<p>答：晚高峰拥塞会拉长往返时延，触发读超时，表现为"断线"。先把读超时放宽到 120 秒观察是否缓解，缓解了就是超时设置问题；仍然断，再看丢包率和代理侧的连接数上限。</p>
<h3>重试时换出口会不会影响账号？</h3>
<p>答：会有影响。换出口意味着登录地变化，短时间多次变化更容易触发额外验证。建议重试保持同一出口，把换出口作为最后手段，并且限制频率。</p>
